# PC1选区与区1的50毫米停靠路线

2026-10-25，本节点为候选GC-BASE-0.3.20，仅完成PC离线、CubeMX和Keil验证。没有访问树莓派或真实串口，没有烧录、清故障、使能或运动。最后确认烧录版本仍为0.3.19；不能据历史状态宣称当前设备无故障。

## 选区与启动

用户确认PC1公共端接两档开关，一档接GND、另一档断开，内部上拉。低电平选择区1，高电平选择区2，稳定50ms才有效。两个启停区车头均沿地图+X，区2首先倒车斜行至扫码点；拨档只是选择配置，不能测出或改变实车位置，仍需人工摆在所选区标记。

PC0继续采用稳定松开→按下消抖30ms→PB0短鸣150ms→一次启动。等待60秒未按会取消，故障、STOP或会话变化均不自动重准备、重发动作或续跑。

启动前拨动PC1立即使旧准备失效，原因5为选区变化。开关重新稳定后，主控在同一配置/会话、连续odom下选择另一条冻结路线，签发新票据；PC0若一直按住，必须再次松开后按下。短鸣结束产生启动事件后锁定选区，运行中拨档不能改变本轮路线。结束或故障后不会自动开始下一轮。

统一配置version9与两条路线明确绑定；旧version5的区1BatchRefs、version8的区2Start2Refs保留，不把新停靠目标混进旧实测记录。板端version9未选区不能ARM，错误区目标、跳段和速度篡改均拒绝；准备与ARM还核对boot/session、票据、选择代号、停车、反馈、故障及机构所有权。

## 协议与目录

`Control/start`复用原PC0状态机，新增无IO的Select消抖和准备绑定；`Board/base_port`是PC1唯一GPIO采样入口。59准备仍接受旧8字节票据/版本；version9必须提供16字节`<4I>`票据、配置版本、区号、选择代号。60查询schema3：原schema2的84字节后附6个uint32（原始电平、稳定区号、有效标志、选择代号、锁定区号、锁定代号），含OK共109字节。Python兼容schema1/2/3，过期选区不作为默认区1。

`robot.nav.selection`只读取和校验冻结包，`robot.drive_core`继续拥有唯一串口。通过`--switch-zone`选择新入口，默认只是预览，不打开设备；显式执行仍需本次现场许可、串口和候选参数确认，并等待PC0。

```powershell
# PC仅预览；不连接任何设备
$env:PYTHONPATH = 'pi'
.\.venv\Scripts\python.exe -B -m robot.drive_core --switch-zone
```

空闲观察期才自动查询PC1状态，运动期间不增加该轮询负担。只读START_STATE应答可以先完成，正式命令在唯一队列中随后发送，不将只读轮询误作另一条动作。250ms反馈过期、500ms主控保活、CAN真实错误、偏离、动作期限和故障停车均保留。

`.ioc`已增加PC1上拉输入并实际CubeMX重新生成，PC0/PC1共用GPIOC输入初始化，不加EXTI；PB0初始高，PWM默认不启动，SWD和原外设参数保留。Keil同步恢复生成器丢失的xsi schema属性，并按摘要生成Start1Refs；生成区的App初始化/调度用户段经检查保留。
