# CAN发送错误：只读分析与离线验证

本轮仅分析既有UART/RAM文件及新旧源代码，构建主机夹具。**未连接设备、未重新开串口、未停核/复位、未清故障、未烧录、未触发动作，固件源码未修改。**
保留上一轮实车LOCKED/0x800结论。原记录见[只读验收](readonly_20261024.md)，现有Web机械页增加“CAN离线分析”。

## 已确认与不能推出的结论

| 证据 | 能确认 | 不能推出 |
| --- | --- | --- |
| TSR=0x1C000009 | mailbox0的RQCP=1、TERR=1，TXOK=0、ALST=0 | 不能将它当作一次普通仲裁丢失忽略 |
| HAL错误0x1000 | HAL_CAN_ERROR_TX_TERR0 | 不是执行器0x800，二者属于不同错误空间 |
| ESR=0x00080040 | LEC=4隐性位错误，TEC低8位=8，冻结时无bus-off | 最近一次不属于LEC=3的ACK错误；但无法代替前7次/首次错误细节 |
| ID0x300、3A 6B | 最近一次失败为ID3状态查询 | 不能据此认定ID3驱动器损坏 |
| errors=8、arbitration_lost=4 | 真实错误和纯仲裁分别计数 | 不能用4次仲裁解释掉8次真实错误 |
| tx_timeouts=0、rx_overflow=0 | 记录中没有50ms发送期限耗尽或接收环溢出 | 无法排除其他电气、节点时钟或回包时序问题 |
| 当前ESR后来为0、接收仍推进 | 后续传输可恢复 | 不表示故障已经清除，软件锁存仍为1 |

LEC由硬件记录，成功传输后可能变为0；参照[ST RM0090的bxCAN错误状态寄存器](https://www.st.com/resource/en/reference_manual/rm0090-stm32f407-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)。
HAL库自身的`HAL_CAN_IRQHandler()`在TERR0分支生成0x1000，仅在启用LEC细分通知时再添加BR等细分位。
当前`Base_Init()`启用TX邮箱、总错误、bus-off等通知，但没有启用`CAN_IT_LAST_ERROR_CODE`，因此**HAL只有0x1000与冻结ESR有LEC4并不矛盾**。
本轮没有为了增加诊断去修改任何板端中断配置。

## 离线回放：实际HAL入口

`tests/test_can_irq_evidence.py`从本仓库HAL库原样提取`HAL_CAN_IRQHandler()`到忽略目录，以库内寄存器常量构建主机夹具，
连接正式`can_tx.c`。只模拟寄存器及HAL底层读写，没有连接设备、没有改变正式传输实现。

1. 输入现场TSR/ESR、ID3查询：得到TERR、失败、隔离、不重发；错误帧快照保留。
2. 只在主机模型打开LECIE：HAL细分为0x1040（TERR0+BR），仍只计一次真实错误并失败。
3. 纯ALST只增加仲裁计数，原期限内重试，不伪造TERR。
4. 仅保留LEC4而没有TERR/TXOK：不伪造发送错误，未完成事务到50ms后按超时失败。
5. TXOK伴随旧LEC值：不会据旧LEC额外计真实错误。
6. 负对照：仅在主机临时副本删除`HAL_CAN_ResetError()`，夹具能检出HAL旧错误累积；当前正式源通过。

HAL局部错误位复位是既有传输实现，不等于解除执行器/总线故障锁存；本轮没有向设备执行该操作。
以上能验证**软件如何解释标志和停车**，不能用注入的硬件标志证明是什么物理因素产生该标志。

## 条件性回包冲突模型

协议构帧与解析确认：某地址请求和回复都使用`address<<8`的扩展ID，且为数据帧。
例如ID3的请求`3A 6B`为2字节，状态回复`3A status 6B`为3字节。
假如两者恰好同时起发，标识符无法区分它们，差异会落在DLC/数据阶段；不能用不同ID的无损仲裁机制解释这种差异。
协议依据见[Bosch CAN用户指南（Keil官方文档库）](https://www.keil.com/dd/docs/datashts/silabs/boschcan_ug.pdf)。

构建了保留原5ms请求间隔的条件性反例：人为设回复延迟10ms，第三次请求SOF可与第一次回复SOF重合；
改为等待匹配回复结束再保留2ms周转，模型中不再有该起发重合。延迟超过模型100ms回复期限则停止，不自动重试。
请求帧0.2ms、回复帧0.25ms及10ms延迟均为**模型假设，不是本车测量值**。
普通帧区间重叠不算证据：CAN载波检测会等待忙总线，本模型仅检查同一SOF；未模拟物理波形、重同步和错误帧。

因此“同ID回包同时起发”是可检验候选，**尚未证实为这次故障的现场原因**。
现有UART RTT约15ms、缓存帧龄上限59ms都不是CAN驱动回复延迟，不能拿来直接调大周转常量。

## 用户补充的拓扑与下一步

用户确认6台驱动器，地址1～6不重复；终端在CAN模块及最远端；总长约30cm，已有跑图成功记录。
这不是当前有效终端阻值、共地/供电或波形的测量结果；本轮不拆线、不加减终端电阻。

后续候选应先移植旧轴查询的匹配回复屏障，补正式调度对照：按地址、命令和RX序号匹配回复，
STOP可抢占，取消后不续发旧查询，原50ms发送期限及250ms反馈过期保护不放宽；运动包不因TERR重发。
必须保证运动中必要轮反馈优先，不能因等待低优先级诊断回复而阻塞STOP或拖过反馈期限。
若获准更新固件，优先补**首次CAN错误**及故障前TX/RX有界历史，保留现有最新快照，避免后续错误覆盖唯一现场。
物理链路测量、重新上电或现场对照采集需另行通知确认，本轮不执行。
