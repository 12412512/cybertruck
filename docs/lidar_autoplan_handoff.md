# 雷达到自主规划的接入准备

最新校准事务代码、原8000网关和树莓派只读准备已接入，见`docs/lidar_calibration_link.md`。以下“09入口尚未接入”属于前轮准备状态；当前受控提交代码已离线通过，但实际部署写入开关仍关闭，未执行真实校准。

## 已完成的链路

原8000工作台继续保存路线、速度、工位间隙与人工障碍。当前模拟雷达流程复用`robot.lidar.protocol/replay/planning`，规划只调用`robot.workbench.planning.make_plan()`，轨迹继续通过`robot.nav.bridge.prepare()`进入原执行器协议模型；没有另建规划器或设备所有者。

2026-10-25新增安装与坐标核对页。`config/lidar_installation.json`仍为安装参数唯一来源，页面JSON是从该配置及已结束扫描导出的版本化摘要，不是生效配置。几何、坐标配准和页面摘要分别归`lidar/geometry.py`、`lidar/calibration.py`、`lidar/review.py`。正式模块不从tools导入实现。

新增本地导出命令：

```powershell
.venv/Scripts/python.exe -B tools/export_lidar_review.py --source output/lidar-live/scan_zone1_20261025 --output pi/robot/web/static/lidar-review.json
```

只读取保存的JSON，不扫描、不连接串口，不重启任何核心。页面只GET摘要，显示：

- 用户安装参数与名义O/雷达位置。
- 三个拟合参考标记、未参与拟合的P4及诊断预测。
- 静态扫描历史、坐标、道路覆盖和树莓派接入分别处于哪一步。
- PC1选区、PC0启动、扫描、规划、唯一执行器的后续调用顺序。

本轮只刷新浏览器即可加载新静态资源；不需要用户重新运行进程重载脚本。没有更改路线、速度、示教草稿或原8000模型进度。

## 实车尚未开放的部分

厂家GRID/RESULT是已套用厂家区号和保存位姿的场地坐标；它不是`lidar_local`，不能直接再加(0,-145)mm安装偏移。旧工程只对该坐标保留未配准状态，未提供可复制的本车场地转换。当前诊断反射假设不是厂家坐标定义。

原四点与固定同点复扫记录保留；独立P4误差35.28mm，原30mm诊断目标未通过。这个数不单独证明硬件有故障，也不代表雷达必须达到抓放精度；后续粗规划必须同时明确坐标定义、位置不确定度、遮挡和道路覆盖，不能拿空输出放行全场。

当前`robot.nav.bridge`只输出`domain=simulation/executable=false`的联调包，实车固件仍只接受原已验证的受限入口。没有因为Web显示了新路径就扩展实车动作白名单。动态计划的板端接入需要另做版本与执行验证，必要时烧录前按用户要求通知。

## 树莓派每轮自主规划的目标流程

1. 控制核心取得PC1稳定区号，绑定本轮起点、安装/地图/标定版本及Web保存参数；等待PC0期间变更区号或版本使本轮准备作废。
2. PC0启动一次任务，静止状态下由唯一雷达核心获取本轮扫描，必须完成对应区号、完整结果及停止确认。
3. 校验扫描身份/时效、坐标版本、有效覆盖及故障停车条件。观测只影响有覆盖证据的道路，其他道路保持未知；不沿用旧扫描或把未知设开放。
4. 同一个规划器根据本轮障碍生成路线，以路线摘要绑定扫描ID、参数版本、起点和速度。无路则给出原因并保持停车。
5. 唯一STM32执行链逐段运行；保留250ms反馈过期、CAN真实错误、保活和故障停车。浏览器关闭不影响控制核心调度。

以上是接入契约，当前不是已部署的实车自动任务。PC端完成后，复用同一Python模块和正式C参考计算，在树莓派构建对应平台的主机库，再做设备验收，不复制一套Web控制逻辑到树莓派。

## 本轮验证与证据

42项雷达/扫描/安装/配准/摘要Python回归，以及11项核对页和13项实机雷达前端检查通过。覆盖独立点不能重新纳入拟合、摘要即使假设通过也不升级许可、采集身份/停止/坐标不一致拒绝，以及原合成绕障到执行链回归。

区1/区2到扫码点的合成障碍模型分别完成3段，21.462/21.132秒，均确认停车、包含10731/10566次扫掠样本检查；这是内存协议与独立Plant模型，不是实车耗时。两批完整路线的对应结果另归同一证据根目录下的`start1_batch/start2_batch`。

两区两批完整合成绕障模型均11段，完成时间分别105.126/103.278秒，停车确认通过，扫掠检查52563/51639样本。速度档仍为0.30m/s/100RPM，没有用提速掩盖绕障成本；结果不代表60秒目标达成，也不代表实车两区新路线已经接入。

## 两点校准准备

用户已确认有两根约50mm直径、高至少100mm的不透明圆柱。当前仅确认器材，没有安排摆放、发送09或写Flash。按厂家上位机说明，校准使用场地中心和对面启停区中心两柱，保持雷达水平并移走其他障碍；两个区独立校准，校准成功会保存当前区位姿。

后续用户已完成区1和两柱摆放、确认雷达人工展开固定、PE14不使能，并提供黑色圆柱50×100mm规则规格。只读预检当前CAN0x800锁存，停车有效/PWM0；没有扫描或保存校准。该后续现场见`docs/lidar_field_session.md`，不能将上段器材准备或旧无故障窗口当成当前验收。

已完成纯离线`vendor_calibration.py`，对照SDK解出0x88的15字节结果，检查新保存序号（含回绕）、source_zone、当前区结果与保存位姿相符、另一区未改变。即使一致也不授予地图配准或运动；旧缓存、倒退序号、错区/布局/位姿均拒绝。默认frame白名单仍拒绝06/09/11，真实写入入口尚未接入，不能把解码检查通过称为设备校准已完成。

正式接入前需在唯一雷达核心准备完整事务，而非浏览器直接发串口：备份新鲜HELLO与13存储记录，核对当前区及停车；09受理后等待当前区最终校准事件和匹配的持久状态，随后核对HELLO和停止。厂家SDK校准结果为15字节，包含区号、保存位姿、偏移、朝向修正、残差和柱距误差；只有ACK不能算成功。当前协议发送白名单尚未加入09，真实校准入口未开放。

使用当前地图定义，区1对面的区2中心是地图(2250,2250)mm，而厂家资料中的对面区中心为其坐标(150,150)mm；不能把两组数字直接视为同一坐标，必须用实际工位身份建立对应。下一次先统一告知摆放与备份/保存范围，得到本轮确认后才执行；此准备不授权当前设备写入。

PC0后自主扫描与规划同样是目标流程。当前板端PC0用于启动已准备的受限路线，新主控任务模式须确保旧准备票据不会在扫描前误启动；该按键事件/任务与路线准备握手尚未实现，不能把文档顺序当作当前固件行为。
