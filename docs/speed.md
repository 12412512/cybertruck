# 离线提速与启停区返航

2026-10-24，从 `b84103f / v0.10.0-flow-sim` 推进，节点 `v0.11.0-speed-parking-sim`。用户确认返航只需在所选启停区内停稳，不要求原中心点或出发朝向。本轮仍仅离线、主机模型与本机只读Web，不烧录、不清故障、不连接真实串口或触发实车运动；旧工程与Pi8080未改动。

## 为什么之前只有0.14m/s

0.14m/s是上一节点为量化“减少停车”收益而保持的调试上限，不能据此认定硬件提不上速度。当前还同时存在0.7rad/s角速、0.25m/s²线加速度、0.8m/s³线jerk、低速接近档和模型100RPM轮目标上限。本轮显式对照0.14/0.22/0.30/0.36m/s，不改后四类限制，也不把模拟速度写入实车配置。

轮速预检原来把全路径最大平移速度和最大角速度直接相加。对于“直线巡航、窗口内低速转姿”的参考，这两个峰值可能发生在不同时段，导致不必要的候选拒绝。现在正式C `Ref_TurnSpeed()`求航向变化区间的平移速度上界：

- 截取真实查时边界，覆盖全部相交的分段速度二次多项式。
- 检查两端与加速度零点，最多15×3次；不假定浮点二分边界恰好落在匀速段。
- 用正式几何导数界和float舍入余量转成平移上界。`Ref_Bounds`仍覆盖完整区间，继续用于车体扫掠。

轮速按 `max(√2×全程平移界, √2×转姿期间平移界 + (半轴距+半轮距)×角速界)` 换算RPM。这仍是对所有车身方向的保守上界，不用稀疏采样代替证明；测试另外以4001个时刻、正式C逆运动学独立核对。

请求巡航速度是上限，不能强制每一段达到它。某候选超出轮速界时，规划器最多4次降低该段线速并重建正式参考，曲率档与末端档同步取更低值；保留V/A/J、车体扫掠和停车门槛，仍不合格才拒绝。这样避免全局档位提高后反而删掉连续连接、增加停车。每段实际线速上限保存在计划的`cruise_m_s`，与全局请求值分开。

诊断阶段只放宽轮速预检、尚未加入自动降档时，0.36档出现17个动作、102.53s；降档后同一“原中心点、朝向自由”对照为9个动作、91.69s。失败与较慢的中间结果保留在output/speed/final、adaptive，不冒充当前区域返航结果。

## 返航区域如何选择

出发朝向和扫码/机械作业朝向保持原确认。仅返航目标改为区域条件：在所选蓝区中，为0/90/180/270°分别求主体投影能完整停入的中心区间，留4mm名义停放余量，再取靠近该区拓扑入口的候选位置。带朝向A*在有效候选中按参考耗时选择；不强制原中心点和出发朝向，也不声称已经搜索所有连续角度与区域位置的全局最优。

终点低速接近仍保留，控制器跟踪已选终点的稳定航向；“返航朝向自由”不表示允许末端持续旋转。最后仍需零速批次确认、发送后新反馈及150ms稳定窗口。导航完成前额外检查模拟odom与独立Plant的主体投影均完整进入所选蓝区；未进入就冻结为失败，不以中心点进入或参考计时结束代替停车完成。

完整突出物、载物包络和现场配准仍未测齐，4mm是名义模型余量，不能作为实车许可。真实包络装不进区域时应明确无可行停车姿态，不能隐去突出物或放宽场界。

## 重现与边界

```powershell
.\.venv\Scripts\python.exe -B tools/build_odom.py --output output/native/speed.dll
.\.venv\Scripts\python.exe -B tools/tune_nav.py --library output/native/speed.dll --output output/speed/region
.\.venv\Scripts\python.exe -B tools/tune_nav.py --library output/native/speed.dll --output output/speed/region --collect
```

`--case`可重复选择场景，独立进程可并行运行不同case，然后collect核对全部源码/配置/库SHA256一致；不混入旧结果。失败档保留状态与原因，汇总不把它算成通过。
