# 首次CAN错误与匹配回包调度

候选 **GC-BASE-0.3.12仅完成离线验证和Keil编译，未烧录**。板端最后确认仍是0.3.11。
本轮未访问串口、SSH或SWD，未复位、清故障或触发运动；原RAM/UART证据未覆盖。
软件验证不证明同ID回包冲突是实车故障根因。

## 首次记录

沿用唯一`Device/can_tx.c`，新增`can_capture`：环形保留最近64条TX提交、RX有效帧、TXOK、ALST、真实错误、取消及发送超时。
每条40字节，包含事件序号、本机毫秒、类型、ID、长度、8字节内容、TX事务序号及TSR/ESR。
首次真实HAL错误回调（含接收读取失败）冻结首次字段与历史；后续错误、STOP或Bus_Rearm不覆盖，无清空命令，重启才重建。
首次字段保存时刻、HAL错误、IRQ入口寄存器、TX/RX序号、当前帧、邮箱和分包状态；原can_diag最近错误及计数保持。
ISR仅定长搬运，不等待、不打印；短RX帧未使用字节清零。

时间是MCU观察到提交/回调的HAL毫秒，不是总线SOF或设备采样时间。同毫秒事件可排序，但不能直接证明物理同时起发。
冻结后不追加，不能从首次历史推断后续错误；发送超时沿用既有保护，不冒充HAL的TERR事件。

## 查询调度

复用旧`智能搬运小车/User/Mech/axis.c`的发送/匹配回复两阶段，仍由当前Bus统一管理：

1. 0x33/35/36/3A单帧查询接纳时记录RX屏障、TX事务序号和起始毫秒。
2. 原50ms发送期限、纯ALST有界重试、真实错误不重发保持。
3. TXOK后仍BUSY；Drive_Parse校验通过、地址和命令匹配、RX序号更新、接收不早于TXOK且在期限内，才接受回包。
4. 回包后留2ms周转再交接；原5ms最小发起间隔保留。
5. 接纳起100ms无有效回包，锁存BUS_ERROR_REPLY=16，清运动队列、保留必要四轮STOP，不自动重查或重放运动。按时回包可以在期限之后结束2ms周转。
6. STOP可取消等待；空闲诊断等待期间的真实CAN/RX错误也立即故障处理。

0x42多帧配置沿用原调用者独占、收完整配置后释放的行为，不套单帧屏障。
使能/速度/位置/STOP的原TXOK语义、四轮批次与ACK观察逻辑保持；回包不证明实物到位。
协议无事务号，无法排除极晚到达且恰好同地址同命令的重复回复；本机屏障只拒绝可判定旧帧。
等待会影响吞吐，后续必须实测回复延迟与运动期反馈帧龄，不能放宽250ms保护补偿。
