# 底盘与机构实车接入准备

2026-10-24，本轮仅本地代码核对、软件测试及Keil编译；没有连接树莓派/串口/SWD、没有烧录、没有使能或机构动作。
继续沿用`http://127.0.0.1:8000/`工作台；机械页新增准备清单和四个料盘命令预设。

## 当前已核对的映射

用户本轮确认全部沿用以下接线。引脚来自`firmware/Car.ioc`，逻辑通道与机构执行参数来自
`firmware/User/Config/mech_hw.h`；`config/mechanism_installation.json`只保存用户确认和料盘用途。

| 对象 | 映射 | 单位与正方向 | 本轮证据 |
| --- | --- | --- | --- |
| 四轮 | CAN ID1/2/3/4，沿用`base_trials.json`及生成`addresses.h` | 车体X前/Y左，逆时针为正 | 既有底盘执行回归；没有本次设备读取 |
| 升降 | CAN ID5 | 下降为正；反馈符号+1；初始0～49mm | 用户确认；旧轴配置/验证记录 |
| 伸缩 | CAN ID6 | 伸出为正；反馈符号−1；初始0～50mm | 用户确认；旧轴配置/验证记录 |
| 料盘 | PE9 / TIM1_CH1 | 0～270°命令，500～2500µs | IOC与旧PWM代码；未测本次波形 |
| 转臂 | PE11 / TIM1_CH2 | 359°反向脉宽换算；83°/180°旧候选 | IOC与旧PWM代码；未证明首次输出不会跳动 |
| 夹爪 | PE13 / TIM1_CH3 | 0°观察、60°释放、98°保持 | 旧代码；真实角度、持料均未知 |

料盘**0°为基准**，**30°、150°、270°为三个存料槽**，不是四个槽。
Web预设只填入命令草稿，不自动执行，也不代表三个槽与夹爪/相机均已标定。

## 本轮实际代码

- `Device/drive.c`增加`0x33`目标位置查询构帧/解析，复用现有带符号幅值、校验字节、地址和接收时间。
- `Control/mech_guard.c/.h`为独立、无IO的被动校验模块，已纳入Keil工程，但**未绑定App、Comm或CAN接收**。
- 保存两轴各自的速度35、实际位置36、驱动状态3A、目标位置33，以及接收序号和采集tick。
- 复用旧`Mech/axis.c`的人工基准、目标/实际静止一致、反馈时效和实测换算思想；不复制旧`mech_io.c`的CAN中断、私有队列或HAL发送。
- 换算仍为升降每320脉冲4098µm，伸缩每320脉冲12400µm；6554编码器单位/320脉冲。
- 相对人工基准的正目标采用向内取整：升降49mm=3826脉冲、43mm=3357脉冲，伸缩50mm=1290脉冲。
- 舵机公式仅提供脉宽预览。未加入PWM启动函数，未增加机构命令入口，未改变当前底盘路线白名单及故障保护。
- `pi/robot/device/integration.py`只读本地映射，为同一Web提供准备状态；不导入串口、不读取真实设备。
- 旧模块只读核对时的SHA256保存在`docs/mechanism_sources.json`，不复制旧工程整树或编译产物。

不能将本轮C模块称为已完成的机构执行器：目前没有轴命令调度、ACK/完成/停止确认状态机、舵机输出适配或新的板端机构上报。

## 人工建零的准备条件

1. 两轴没有实体限位开关，最高点和最近端需人工复现；应先支撑升降机构，避免断电下坠，不强推通电锁定的传动。
2. 放到基准的机械操作须单独确认。重新上电/复位/USB打开导致复位后，建立新boot/session；旧零点不继承。
3. 先只读核对两台电机配置，沿用旧工程每台三次一致读取及完整原始配置检查；本轮`Mech_Config`只接收未来配置审核器的结果，不自行把一次通用配置解码当完整审核。
4. 同时具备八类真实反馈，全部新鲜≤250ms；速度为0、驱动状态正常、目标与实际差≤16编码器单位。
5. 至少五个完整新反馈轮次，连续稳定≥300ms，实际和目标均相对稳定锚点偏差≤8单位。重复轮询、重复帧、旧序号不增加稳定证据。
6. 人工明确确认“最高/最近端”后，分别记录实际位置基准和驱动目标基准，仅写RAM的软件参考，不向驱动器写永久零点、不回零搜索、不自动使能。
7. 已有效时拒绝再次捕获零点，不能用清零掩盖位移。失联、错误反馈、越界、配置变化、人工移动或会话改变使参考失效；故障不能由普通停止清除。

当前模块只置`stop_required`诊断标记，**尚未连接真实停止调度**。未来正式机构执行器必须将该标记接到唯一STOP通道，确认两轴停车；不能把置位当作电机已停。

## 互锁与首次PWM

- 新目标必须持有当前零点版本、当前基准有效、底盘已停、反馈新鲜且静止稳定。
- 初始49/50mm命令范围不扩大；反馈允许300µm容差，命令限位不增加容差。
- 下移前伸缩收回≤1mm；伸出>1mm前升降至少45mm且转臂命令参考已知为180°。
- 转臂/料盘旋转前两轴均回到基准1mm内；料盘还需转臂180°避让参考。
- 这些阈值沿用PC模型的保守代理，未经过真实包络证明；接实车后只能作为初始受限试验条件。
- 上电PWM保持不启动。模拟“锚定”不能复用于实车；首次输出前必须核对实际转臂/料盘/夹爪姿态及独立目标，不能默认直接发180°/30°/0°。
- 故障时停止底盘和两轴，夹爪保持原命令；不自动张爪、收臂、回零、清故障或续跑。

## 后续接入顺序（同一Web）

1. **通知用户后连接**树莓派和开发板，只读核对当前固件、boot、故障、停车、USB身份/稳定性及IMU时效；旧记录不代表本次状态。
2. 复用现有`drive_core`/`device.execution`的会话、动作ID和反馈逻辑，接入统一设备所有者。旧`car-web.service`不重新启用，网页不直接打开串口。
3. 在唯一CAN调度器内增加ID5/6的有界读取，不另装CAN中断。先验证轴配置和八类反馈，测量轮/轴查询时延；不得挤占运动中四轮的250ms保护窗口。
4. 机构仍保持动作禁用，先接板端只读机构状态。STOP必须覆盖本次已拥有的机构地址，记录首次故障与触发帧。
5. 待新固件编译、测试通过，烧录前通知；烧录后先告知并只读验收，等待本次新的现场确认后才能进行单个机构动作。
6. 验证人工基准复现、轴方向/实际距离、单个舵机首次输出，随后才做三个料位示教和单件转存。
7. PC模拟与实车在同一工作台使用不同数据域和状态源；模拟位姿/零点/成功结果不填入真实字段。当前没有实车模式切换或实车使能按钮。

当前PC准备清单读取本地源码。后续部署Pi时需导出带源哈希的映射清单随配置部署，不要求复制旧工程或整份固件源码；网页与控制核心接口继续沿用。
