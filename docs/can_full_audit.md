# CAN收发链审查（2026-10-26）

## 结论与范围

本轮检查 can_tx、bus、base_port 的错误传播、HAL中断处理、查询匹配及旧工程轴查询方式。不是对全部视觉、导航和Web模块的完整审计。未连接设备、复位、清故障、烧录或动作。

换CAN模块后的30.109秒实测已有记录：真实错误1→5，查询超时0，四轮反馈最大66ms；首次ID4/35，最近ID3/3A，TERR0/LEC4。故障跨节点与命令，不能确定为ID6单节点问题，也不能凭换件排除所有物理原因。

## 本轮修复

- can_tx.c：错误已置tx_bad后，迟到完成回调不再更新tx_done_sequence或写DONE记录。原执行状态仍有故障门禁，因此这是成功证据污染的修复，不能声称它造成了现场TERR。
- bus.c：CheckErrors每个计数只读取一次，判断与seen记账使用同一值；取消过程中新增错误留到下一轮，避免多次读取volatile计数吞掉变化。
- bus.c：同轮CAN错误及RX溢出分别保留标志，替换原来的二选一错误分类。

## 未改变与尚未定因

原50ms发送、100ms回包、250ms反馈、500ms保活及STOP优先级不变。真实错误仍锁存。查询须TXOK及匹配新回包，FD/F6/F3不自动重放。

现有NART单次发送策略会将一次真实TERR升级为故障；这是明确策略，不是凭软件即可认定的硬件错误根因。历史计数与活动故障当前耦合，若以后采用只读查询有界恢复，必须同时设计失败升级和事件审计，不能单独屏蔽errors或全局开启自动重发。本轮未实施该策略变更。

旧工程轴查询完成后10ms间隔已在当前机构查询中复用。当前六节点模型正常最大119ms、7ms延迟239ms；8ms延迟259ms仍被原时效门槛拒绝。继续增加固定间隔可能损害250ms反馈要求，不作为未经证实的修复。
