# Web人工故障恢复

2026-10-26，GC-BASE-0.3.33。用户希望自行获取控制权，并通过页面恢复初始准备状态、清除处理后的锁存故障。原61正常STOP入口继续保留；新增65为明确的人工重启事务，不让61或Bus_Rearm忽略真实CAN错误。

## 操作

先停止并修复故障，确认机构静止、夹爪空且机构已有支撑，勾选页面现场确认，再点击“清除故障并重新连接”。恢复会关闭三路机械舵机PWM、重启STM32，使原会话、零点及舵机参考失效。动作目标和参考输入默认空白，0°/180°不再自动填作当前姿态。

恢复检查通过后，用户自行获取控制权、建零和记录真实参考，再明确执行目标。保存的姿态与联调表版本继续保留，不自动执行、重抓、回原点或续跑。PE11方向和实际零位仍需小角度核对；本次没有反转原PWM映射。

## 执行和限制

唯一DeviceCore接收recover请求，要求0.3.33机械许可、同一新鲜会话、STOP已应答、底盘停车、机构配置3/3、无人持有控制权，且三个明确确认（故障已处理、静止现场确认、关闭PWM后的机构支撑）为真。仅点击获取控制权不能清故障。缺反馈或仍断线时不开放恢复。

device/recovery.py先将状态落盘，再通过38读取完整首次CAN错误及冻结历史；有记录时读取0～count页，无记录时保存合法空页。分页校验、身份变化、归档写入失败或请求超时都中止，不发送重启。分页之间保留35/58正常轮询和保活。归档为运行目录fault_recovery/<id>.json，包含前后状态与恢复阶段，不保存口令或控制令牌。

正式65为16字节：递增请求号、magic0x52454356、确认位图7、零点版本。板端要求当前四轮停车确认及新鲜稳定反馈、两轴八项反馈均≤250ms、速度0、驱动无故障位；不要求中断动作的实际位置必须等于旧目标。活动底盘、旧请求号、错误参数或过期反馈拒绝。

接受后只请求停车并关闭PWM，保留故障计数直到复位；PWM关闭失败不安排复位。延迟至少250ms用于发送ACK及停车，再次核对静止才执行一次NVIC_SystemReset。2秒仍不能确认静止则取消；STOP可取消尚未执行的复位，重复旧请求不能再次复位。原250ms反馈、500ms主控保活及CAN真实错误保护不变。

主机收到明确接受后，只建立一次新的握手流程。必须看见不同boot、相符固件、新鲜无故障停车、两轴只读附着/配置3/3、PWM0、零点无效、动作编号0，持续核对后才报告DONE。恢复期间不授予控制权，故障仍存在或失败时锁定，不自动重启第二次。
